  шпиле, и это обрыв на границе кластера. Заменить на мягкий бонус.
- **«Гарантированно в конец списка» — неверно:** в пресете «Такси» BV9300 Pro без бонуса обгоняет типичный

- **В ТЗ нет ни одной метрики качества.** Минимум: силуэт и ARI по сидам в каждом шпиле, 5 sanity-тестов и

## 2. Критические ошибки (ломают математику)

### 2.1. Расстояние от вектора весов W до центроидов (п. 4.2)
**Суть.** $W$ — это важность осей («насколько мне важна батарея»), а центроид $c_j$ — значения на осях («какая
батарея у типичного телефона кластера»). $\|W - c_j\|$ — разность величин разной природы.

**Почему ломается.** Возьмём пресет «Такси»: $W=(1{,}0;\ 0{,}7;\ 0;\ 0{,}1)$ по (active_h, perf, camera, hz).
Пусть кластер A имеет центроид $(0{,}9;\ 0{,}6;\ 0{,}5;\ 0{,}5)$ (автономный и шустрый), а кластер B —
$(1{,}0;\ 0{,}7;\ 0;\ 0{,}1)$ (просто совпал с цифрами весов). Евклид выберет B, хотя по смыслу A лучше для
таксиста. Хуже того: при весах 0 по камере выигрывает кластер с **худшей** камерой, хотя пользователю она просто
безразлична. Плюс у пресетов разная длина $W$ (3–4 признака), а центроиды живут в пространстве всех признаков
кластеризации (у нас 9–18).

**Минимальный фикс.** Достроить $W$ до полного пространства признаков нулями и брать кластер с максимальной
полезностью центроида:

$$
j^* = \arg\max_j \; U(c_j) = \arg\max_j \sum_f W_f \, c_{j,f}
$$

```python
W_full = np.zeros(len(FEATURES)); W_full[[idx[f] for f in preset]] = list(preset.values())
target = int(np.argmax(centroids @ W_full))          # centroids: (k, n_features), та же шкала, что и X
```

Надёжнее вариант, который **уже стоит в коде** (`PhonePipeline.cluster_features`): целевой кластер — тот, где
лежит телефон с максимальной полезностью **для этой анкеты** (учитывает бюджет и штрафы, а не только центр).

### 2.2. MinMax без защиты от `max == min`
**Суть.** Деление на ноль при постоянном признаке внутри шпиля. Реально случится: `nfc`=1 у всех флагманов,
`is_ios`=0 во всём бюджете; в среднем шпиле частота экрана почти вся 120 Гц.

**Фикс.** Знаменатель заменять на 1 и ставить балл 0,5 (нейтральный). Так уже сделано в
`src/preprocess.py::MinMaxScalerCustom`:

```python
den = np.where(x_max - x_min == 0, 1, x_max - x_min)
score = np.where(x_max - x_min == 0, 0.5, (x - x_min) / den)
```

### 2.3. Бинарные признаки в MinMax рядом с непрерывными
**Суть.** У `has_ois` (0/1) размах после MinMax всегда ровно 1, и половина объектов стоит на краях шкалы.
У непрерывных признаков основная масса сжата в середине (см. 2.4: 90% бюджетных моделей укладываются в [0;0,38]
по батарее). В евклидовом расстоянии **бинарный признак становится самым тяжёлым**: KMeans начнёт делить
шпиль на «с OIS / без OIS», а не по характеру.

**Фикс.** Множитель $\alpha\approx0{,}3$–$0{,}5$ на бинарные признаки в кластеризации (у нас уже есть экспертные
веса и в `features.py` у eSIM/NFC стоит 0,3) **или** вынести бинарные признаки из кластеризации и использовать
их только в полезности.

### 2.4. «Гарантированно опускается в конец списка» — опровергается
Пресет «Такси», бюджетный шпиль, MinMax как в ТЗ (без клиппирования):
- **Blackview BV9300 Pro:** active_h 34,5 ч = **1,00** (максимум шпиля). AnTuTu 400 тыс. при диапазоне шпиля
  150–1 500 → примерно 0,35 по логарифму. Частота 120 Гц → 0,5. Итого
  $U = 1{,}0\cdot1{,}00 + 0{,}7\cdot0{,}35 + 0{,}1\cdot0{,}5 \approx 1{,}30$, бонуса нет.
- **Типичный телефон целевого кластера:** active_h 12,1 ч (медиана) = **0,22**, AnTuTu ≈0,5, 120 Гц.
  $U = 0{,}22 + 0{,}35 + 0{,}05 + 0{,}4 = 1{,}02$.

«Броневик» **выше**. Утверждение верно, только если $0{,}4 > U_{\text{броневик}} - U_{\text{цель}}$. Но выброс,
максимизирующий главный признак пресета, получает разницу больше 0,4 почти всегда. Причём это даже правильный
ответ для курьера (см. 3.3).

## 3. Поблочный разбор

### 3.1. MinMax внутри шпиля
**Плюсы**
- Сырые значения в базе, баллы на лету — новые модели не требуют ручного пересчёта.
- Локальная шкала делает различия внутри сегмента заметными (бюджетнику не обидно сравниваться с флагманами).

**Минусы и риски (с цифрами)**

| Проблема | Сценарий отказа |
|---|---|
| Выбросы | BV9300 Pro: active_h 34,5 ч при медиане 12,1. Медиана шпиля получает 0,22 вместо 0,35 без него (−37%); 90% бюджетных моделей укладываются в [0;0,38] по батарее. Признак почти перестаёт различать обычные телефоны |
| Нестабильность | Добавили телефон на 11 000 мА·ч → баллы батареи у всех 115 моделей шпиля поменялись. Цифры в отчёте курсовой «поплывут» между версиями базы |
| Сравнение между шпилями | 1,0 по батарее у бюджетника = 34,5 ч, у флагмана = 21,8 ч. Если бюджет пользователя (например, 35 000 ₽) захватывает два шпиля, сквозной топ сравнивает несравнимое |
| Скошенные распределения | AnTuTu в бюджете различается в 10 раз (max/min), камера 8–200 МП, память 64–512 ГБ: без логарифма весь шпиль сожмётся у нуля |

**Что улучшить (сохраняя замысел)**

$$
\tilde x = \ln(1+x)\ \text{для AnTuTu, МП, ROM, Вт, мА·ч};\qquad
x' = \operatorname{clip}\!\big(\tilde x,\ Q_{5\%}^{(\text{шпиль})},\ Q_{95\%}^{(\text{шпиль})}\big);\qquad
\text{Score} = \frac{x' - Q_{5\%}}{Q_{95\%} - Q_{5\%}}
$$

```python
def tier_scale(x, log=False, lo_q=5, hi_q=95):
    x = np.log1p(x) if log else np.asarray(x, float)
    lo, hi = np.percentile(x, [lo_q, hi_q])
    if hi - lo < 1e-9:
        return np.full_like(x, 0.5)
    return np.clip((x - lo) / (hi - lo), 0, 1)
```

- Параметры шкалы ($Q_5$, $Q_{95}$ по каждому шпилю) **сохранять вместе с моделью** и привязывать к хэшу датасета
  (в проекте уже есть `MODEL_VERSION` и `seed_hash`). Тогда пересчёт — осознанное событие, а не дрейф.
- Для сквозного топа (бюджет на стыке шпилей) использовать глобальную шкалу либо показывать топ по шпилям
  раздельно (вопрос 8.3).

**Что заменить, если хочется проще.** Перцентильный ранг внутри шпиля ($\text{rank}/n$): устойчив к выбросам
сам по себе. Цена: теряется «насколько» (разница 5 000 и 5 100 мА·ч равна разнице 5 100 и 15 000, если между
ними нет моделей). 1 час работы.

**Новые идеи.** Не делить по шпилям совсем, а нормировать глобально, и шпиль использовать только как фильтр
выдачи. Тогда баллы сравнимы везде, а «слипание» лечит раздельная кластеризация.

### 3.2. KMeans по шпилям
**Плюсы**
- Деление по шпилям — главный рычаг против слипания. Подтверждено: внутри шпилей самый большой кластер — 34–60
  моделей вместо 179.
- Стабильность приемлемая: ARI по 10 сидам 0,86 (бюджет, k=4 и 5), 0,91–1,00 (средний), 0,73–0,95 (флагман).

**Минусы и риски**

| Проверка | Факт на нашей базе | Вердикт |
|---|---|---|
| Жёсткое k | Лучший k по силуэту: бюджет **2**, средний **5**, флагман **2** (перебор 2…8). Силуэт везде 0,27–0,33 — структура слабая | Жёсткое k не обосновано данными |
| k=6 в бюджете | Размеры кластеров 59/24/20/8/**3**/**1**, ARI 0,72 | Вырожденные кластеры, нестабильно |
| «Броневики» при k=5 | 3 защищённые модели бюджета (Armor X13, BV8100, BV9300 Pro) попали в **три разных** кластера размером 52, 23 и 19 | Кластер «броневиков» **не гарантирован и не получается** |
| «Бюджет забит кирпичами» | Защищённых (вес ≥ 300 г) в бюджете 3 из 115 = 2,6%. Doogee из базы удалён. Armor 28 Ultra из-за цены 51 000 ₽ попал во **флагманы** | Предпосылка неверна для текущей базы |
| Коррелированные признаки | Спирмен: AnTuTu–частота 0,54, AnTuTu–зарядка 0,57, AnTuTu–цена 0,84 | Производительность учитывается ≈2–3 раза |
| Объём | 81–115 объектов на 9–15 признаков и 4–6 кластеров: 15–25 объектов на кластер | Предел. k > 5 в шпиле — шум |

**Ответ на вопрос «гарантирован ли кластер броневиков при k=5».** **Нет.** KMeans минимизирует сумму квадратов
расстояний. Трём точкам из 115 выгоднее «прилипнуть» к соседям, чем занимать собственный центроид. Это видно и на
данных: при k=5 они разошлись по трём кластерам.

**Что улучшить**
1. Флаг «Защищённый» правилом **до** кластеризации:
   `rugged = (weight_g >= 300) | (ip_rating in {IP68, IP69K} & battery_mah >= 8000 & weight_g >= 280)`.
   Защищённые исключаются из KMeans и образуют свой архетип.
2. k выбирать в диапазоне [3;5] по силуэту при условии «минимальный кластер ≥ 8 моделей»:

```python
def choose_k(X, ks=range(3, 6), min_size=8):
    best = None
    for k in ks:
        lab = KMeans(k, n_init=20, random_state=0).fit_predict(X)
        if np.bincount(lab).min() < min_size:
            continue
        s = silhouette_score(X, lab)
        best = max(best or (s, k), (s, k))
    return best[1] if best else 3
```

3. Архетипы не привязывать к номерам кластеров заранее, а **именовать после обучения** по профилю центроида
   (функция `cluster_names` в `clustering.py` так и делает). Ставка «кластер 3 = автономные» без этого ломается
   при любом изменении базы.
4. Коррелированные признаки: оставить один представитель производительности (AnTuTu), а частоту и зарядку
   брать с весом 0,5, либо PCA до 5–6 компонент перед KMeans (PCA — P2).

**Что заменить (оценка применительно к 80–115 объектам)**

| Метод | Плюсы | Минусы | Цена |
|---|---|---|---|
| Agglomerative (Ward) | Детерминирован, есть дендрограмма для отчёта | Те же проблемы с выбросами | 1 ч, уже есть в `compare_algorithms` |
| GMM | Мягкая принадлежность — сразу даёт мягкий бонус (3.4) | Ковариация на 15 признаках при 80 объектах переобучается; брать `covariance_type="diag"` | 2–3 ч |
| HDBSCAN | Сам находит выбросы (броневики → шум) | При n ≈ 100 нестабилен к `min_cluster_size`, много шума | 2 ч, нужен пакет `hdbscan` |
| UMAP + HDBSCAN | Красиво на картинке | **Оверинжиниринг** для 287 строк | — |
| IsolationForest для выбросов | Формально «ML-детектор аномалий» для отчёта | Правило на 1 строку даёт то же самое и объяснимо | 1 ч |

**Новые идеи.** Отчётная метрика стабильности: ARI по 10 сидам и по бутстрепу 80% выборки. Таблица «k →
силуэт / ARI / минимальный размер» по каждому шпилю — готовый раздел курсовой.

### 3.3. Векторы весов W
**Плюсы**
- Явная иерархия «главное / второстепенное / не важно» понятна пользователю и защищаема.
- Для «Игрофона» эффективная частота уже есть в коде (выше 120 Гц коэффициент 0,2).

**Минусы и риски**
- **Разная длина W** (3–4 признака): признаки вне пресета молча получают 0. Для «Фото» это значит, что вес телефона
  в 500 г и отсутствие NFC не важны вовсе. Нужна базовая «гигиена» для всех пресетов: NFC, вес, бюджет как
  штрафы.
- **Двойной троттлинг.** При `cpu_stability_rate` = 0,7: производительность $1{,}0\cdot(0{,}7\,P)$ теряет 0,3P, плюс
  $0{,}5\cdot$active_h «со штрафом горячего чипа» теряет ещё до 0,15. Суммарно Exynos/Tensor теряют ≈0,45 при
  максимуме ≈2,3 — **20% оценки за один фактор**. Больше, чем весь бонус кластера.
- **Числа 1,0 / 0,8 / 0,7 / 0,6 / 0,5 / 0,1 ничем не обоснованы.** Сумма весов разная: «Такси» 1,8, «Игры» 2,3,
  «Фото» 2,4. Значит, и шкалы $U$ разные, а бонус 0,4 весит по-разному (22% / 17% / 17%).
- **«Такси»: защищённый телефон с большой батареей — объективно хороший выбор для курьера** (падения, дождь,
  смена 12+ ч). Объявить BlackView мусором по умолчанию — значит выкинуть лучший ответ для этого пресета.
- **Экспертные индексы** (`brand_photo_score`, `os_optimization_index`): невоспроизводимы. Риск брендового
  перекоса («Apple = 10»), на защите будет вопрос «откуда цифры?».

**Что улучшить**
- Нормировать: $\sum_f W_f = 1$ для каждого пресета. Тогда $U\in[0;1]$ везде, и бонус сравним между пресетами.
- Троттлинг учитывать **один раз**: в производительности $P_{\text{real}} = \ln(\text{AnTuTu})\cdot s$, а в
  `active_h` — только физика (ёмкость, экран, частота), без $s$.
- `cpu_stability_rate` брать из **измеримого** источника: стабильность в стресс-тесте 3DMark (там и считается
  процент) или средний по семейству чипа; пропуски заполнять медианой семейства и ставить флаг `is_imputed`.
- `has_ois` и наличие телевика — из спецификаций (измеримо).
- `brand_photo_score` заменить измеримым прокси: размер сенсора, OIS, телевик, ≥ 3 модуля. Или ввести
  рубрикатор из 5 пунктов по 0/1, чтобы оценка воспроизводилась.
- В «Такси» дать защищённым положительный вес (IP68 / вес как плюс к надёжности), а не отбрасывать.

**Что заменить (калибровка весов)**

| Способ | Что даёт | Цена |
|---|---|---|
| AHP (попарные сравнения, проверка согласованности CR < 0,1) | Веса выводятся из 3–6 попарных суждений Ильи, а не назначаются; легко защищать | 3–4 ч, Илья + таблица |
| Обучение на отзывах (логистическая регрессия «подходит / не подходит» по разнице признаков) | Веса из данных | Нужно ≥ 100 отзывов; сейчас их почти нет → P2 |
| Ранжирование по эталонным запросам (подбор весов под NDCG@5) | Веса под экспертную разметку | 20–30 размеченных запросов, 4–6 ч |

**Новые идеи.** Пресет — это не только веса, но и **жёсткие пороги** (у «Такси» active_h ≥ 10 ч, NFC
обязателен). Пороги объясняются проще весов и сами режут явный мусор.

### 3.4. Кластерный бонус
**Плюсы**
- Простой и объяснимый способ подмешать «характер» телефона к поштучной полезности.
- В текущем коде он уже есть: `score = u_norm + 1,5·P(класс) + 0,4·[кластер = лучший]`.

**Минусы (числа)**
- Масштаб: при $U\in[0;\sum W]$ бонус 0,4 составляет 22% («Такси», 1,8), 17% («Игры», 2,3) и 17% («Фото», 2,4).
  В «Фото» 0,4 = 0,4/0,6 = 0,67 шкалы `active_h` = **≈19 часов автономности** в бюджетном шпиле (размах 28,6 ч).
- **Обрыв:** два телефона с разницей признаков 0,01 по разные стороны границы кластера получают разницу 0,4.
  При слабой структуре (силуэт 0,27–0,33) таких «пограничных» моделей много.
- Вырожденный целевой кластер (1–3 модели при k=6, см. 3.2) или кластер без моделей в бюджете: бонус либо
  никому не достаётся, либо достаётся одному телефону, и он гарантированно первый.
- **Костыль или нет?** Если W хорошо разделяют телефоны, бонус ничего не добавляет. Если плохо — маскирует это.
  Проверяется только метрикой: NDCG@5 с бонусом и без (раздел 4).

**Что заменить: мягкий бонус**

Принадлежность телефона $i$ кластерам — через softmax по расстояниям в пространстве признаков:

$$
p_{ij} = \frac{\exp\!\left(-\|x_i - c_j\|^2 / \tau\right)}{\sum_{m}\exp\!\left(-\|x_i - c_m\|^2 / \tau\right)}
$$

Насколько кластер подходит пресету — через полезность центроидов:

$$
a_j = \frac{\exp\!\left(W\cdot c_j / T\right)}{\sum_m \exp\!\left(W\cdot c_m / T\right)}
$$

Бонус:

$$
B_i = \beta \sum_j p_{ij}\, a_j,\qquad \beta = 0{,}15\cdot\sum_f W_f \;(\text{или } 0{,}15 \text{ при } \textstyle\sum W = 1)
$$

```python
d2 = ((X[:, None, :] - C[None, :, :]) ** 2).sum(-1)          # (n, k)
p = np.exp(-d2 / tau); p /= p.sum(1, keepdims=True)           # мягкая принадлежность
a = np.exp(C @ W / T); a /= a.sum()                            # «подходящесть» кластеров пресету
bonus = beta * p @ a                                           # (n,)
```

$\tau$ — медиана $d^2$ до ближайшего центроида, $T\approx0{,}1$. Обрыв исчезает, вырожденные кластеры сами
теряют вес. GMM даёт $p_{ij}$ «из коробки» (`predict_proba`), это P2. Цена мягкого бонуса — 1–2 ч.

**Новые идеи.** Бонус за **разнообразие** выдачи (не больше 2 моделей одного бренда в топ-5, минимум 3 кластера
в топ-10) решает проблему однообразной выдачи лучше, чем бонус за один кластер.

## 6. Предлагаемая архитектура v2.1

```
сырые признаки (SQLite)
  → шпиль (класс 0/1/2)
  → is_rugged (правило)
  → масштабирование в шпиле: log → clip(p5, p95) → [0;1]   (параметры сохраняются с моделью)
  → KMeans по шпилю без rugged, k ∈ [3;5] по силуэту + min_size
  → имена архетипов по центроидам (+ архетип «Защищённые»)
  → U_i = W·x_i (Σ W = 1) − штрафы
  → мягкий бонус B_i
  → ограничения разнообразия
  → топ-N
```

```python
import numpy as np
from sklearn.cluster import KMeans
from sklearn.metrics import silhouette_score

LOG = ["antutu_k", "camera_mp", "rom_gb", "charge_w", "battery_mah"]
FEATS = ["active_h", "antutu_k", "camera_mp", "rom_gb", "refresh_eff", "charge_w", "weight_g", "screen_in"]


def fit_tier(df_tier):
    rugged = (df_tier.weight_g >= 300).to_numpy()
    X = np.column_stack([np.log1p(df_tier[f]) if f in LOG else df_tier[f].astype(float) for f in FEATS])
    lo, hi = np.percentile(X[~rugged], 5, axis=0), np.percentile(X[~rugged], 95, axis=0)
    span = np.where(hi - lo < 1e-9, 1, hi - lo)
    Xs = np.clip((X - lo) / span, 0, 1)
    k = choose_k(Xs[~rugged])                                   # см. 3.2
    km = KMeans(k, n_init=20, random_state=0).fit(Xs[~rugged])
    return {"lo": lo, "hi": hi, "km": km, "rugged": rugged, "X": Xs}


def rank_tier(m, W, penalties, beta=0.15, T=0.1, diversity=None):
    W = W / W.sum()
    U = m["X"] @ W - penalties
    C = m["km"].cluster_centers_
    d2 = ((m["X"][:, None, :] - C[None]) ** 2).sum(-1)
    tau = np.median(d2.min(1)) + 1e-9
    p = np.exp(-d2 / tau); p /= p.sum(1, keepdims=True)
    a = np.exp(C @ W / T); a /= a.sum()
    score = U + beta * (p @ a)
    order = np.argsort(-score)
    return diversity(order) if diversity else order
```

## 9. Уверенность и оговорки

- **Высокая уверенность:** ошибка W→центроид (2.1); отсутствие кластера «броневиков» и нестабильность k=6 —
  посчитано на реальной базе; масштаб бонуса и пример опровержения (2.4) — арифметика по формулам ТЗ.
- **Средняя:** оценка двойного троттлинга (≈20%) — поле `cpu_stability_rate` в базе отсутствует, взято значение
  0,7 для иллюстрации.
- **Не проверено:** заявленные в ТЗ «k=7, 155 моделей в двух кластерах». В текущем коде k выбирается в [4;7] по
  силуэту; сейчас k=4 и 179 моделей в одном кластере — проблема та же, цифры другие.
- **Данные:** у 60% моделей цена — августовская оценка; часть характеристик новинок оценена; AnTuTu выведен по
  процессору. Это влияет на шпили (35% метки класса — цена) и на абсолютные цифры, но не на выводы ревью.
- **Признаки кластеризации** в проверке: active_h, AnTuTu, камера, частота, зарядка, вес, диагональ, ROM,
  батарея (MinMax в шпиле, как в ТЗ). С другим набором признаков размеры кластеров будут другими, вывод о
  «броневиках» — нет: их всего 3 на шпиль.
